# 改善提案: 野球スコアブックアプリ

作成日: 2026-07-26
観点: 「試合中にベンチからスマホでリアルタイムに使い込める」ことを最優先に、機能・UI・品質の全角度から現状を分析した改善提案。
DB 接続によるデータ永続化は将来展望とし、本書のスコープ外。

## 1. 現状の到達点（前提）

アプリの土台は良好な状態にある。

- テスト 129 件（17 ファイル）green、`tsc --noEmit`・`pnpm build`・ESLint すべて通過
- replay ベースのドメイン設計（イベント＝入力のみ、導出は常に再生）により、編集・削除の整合性が構造的に保証されている
- 過去の検証で指摘した課題はすべて解消済み:
  - 振り逃げの進塁シート接続（`lib/domain/runner-advance.ts` 新設）
  - 編集時の打点フラグ（isRBI）保持
  - アウト超過の violation（`OUTS_EXCEED_HALF_INNING`）
  - フォースアウトで3アウト目成立時の得点無効化
  - 死にコード削除（旧 game-reducer / dummy-game / theme-provider / hooks）
  - 「内野安 = otherOut」の根本修正
- 違反は `lib/app-state/feedback.ts` の日本語辞書経由でトースト通知される
- 下部固定バー（戻す/走塁/結果入力）、確定前プレビュー、2アウト時の併殺無効化、
  safe-area 対応、オフラインバナー（network-status.tsx）など、実戦配慮も多い

### 既に良くできている点（維持すべき設計）

- 主要3操作（Undo / 走塁 / 結果入力）が常時1タップで到達可能（live-scoring.tsx 下部固定バー）

- 破壊的操作（試合終了・打席削除）にだけ確認ダイアログを置く配分

## 2. P1: 入力速度 — 1試合数百タップの積み上げを削る

代表プレーの現状タップ数（コード上のフロー追跡による実測）:

| プレー               | タップ数 | 備考                                     |
| -------------------- | -------- | ---------------------------------------- |
| 三振 / 四球          | 3        | auto-advance が効く最短経路              |
| 遊ゴロ（走者なし）   | 5        | 走者ゼロでも進塁シートで確定が必要       |
| 走者一塁・左前安打   | 5        | 既定進塁が正しく修正 0                   |
| 走者二塁・単打で生還 | 6        | 既定が「二塁→三塁」のため生還への修正 +1 |
| 盗塁                 | 5        | 走者選択 + Select 開閉 + 確定            |
| 6-4-3 併殺 / 犠飛    | 5        |                                          |

1 試合は両チーム 60〜80 打席のため、確定タップだけで 300 タップ超になる。

### 提案

1. **走者に影響しない凡打で進塁シートをスキップ**
   現状は走者不在のゴロ/フライでも情報量ゼロのシートが開く（live-scoring.tsx:115-118）。
   「既定 movements が打者のみ、かつ走者不在」なら即記録に拡張（凡打 5→4 タップ）。
2. **既定進塁に打球情報を反映**
   `getDefaultMovements`（lib/domain/rules.ts:48-53）は打球方向・内野/外野を見ていない。
   - 外野単打で二塁走者生還（最頻ケース）が毎回手動修正
   - 内野安打で三塁走者が自動生還してしまう（逆方向の誤り）
     detail/battedBall をシグネチャに追加し、event-factory から渡す。
3. **盗塁の高速化**
   走者 1 人なら自動選択、進塁先は Select ではなく既定値入りトグル（二盗なら「2塁」初期選択）に
   （base-running-event-sheet.tsx:243-264）。5 タップ → 2〜3 タップ。
4. **三振の一発入力**
   空振り/見逃しの必須選択をやめ、カテゴリ画面に「三振」直接ボタン。種別は後編集で付与可能に。

## 3. P2: 誤入力の防止と復帰 — 速く入れても壊れない

5. **入力 UI に状況ミニヘッダ**
   打席入力ダイアログはモバイルでほぼ全画面（max-h-[92dvh]）を覆い、開いた瞬間に
   「今何回・何アウト・誰が打席か」が見えなくなる。「3回表・1アウト・走者一二塁・打者○○」の
   1 行を各ダイアログ/シートのヘッダに固定表示（修正モードのみ回表示がある非対称も解消）。
6. **進塁シートの出口を整える**
   キャンセルボタンがなく、閉じると選択した結果ごと破棄され最初からやり直し
   （live-scoring.tsx:322-328）。「結果を選び直す」ボタンの追加と、満塁時にスクロール圏外へ
   落ちる確定ボタンの sticky footer 化。
7. **「ホーム」「アウト」の隣接解消**
   進塁トグルは 5 択横並び・各 40px 高。意味が正反対の 2 択が隣接し、誤タップで得点が消える。
   アウトのみ色・位置を分離し、高さ 44px 以上へ。
8. **Undo の安全網**
   Redo がなく、連打で走塁・交代も区別なく巻き戻る。トーストを操作指に近い bottom-center へ
   移し、トースト内に「元に戻す」（Redo 1 回分）を追加。
9. **「進塁だけ直す」編集導線**
   過去打席の修正は必ずカテゴリ選択から再入力（at-bat-result-flow.tsx:94-96）。
   「結果はそのまま、進塁/打点のみ修正」のショートカットを追加。
   打順表セルのヒット領域（36px 高）も 44px へ拡大。

## 4. P3: 記録の正確性・表現力 — スコアブックとしての完成度

10. **編集・削除の連鎖無効化の可視化（最重要の残存負債）**
    過去イベントの編集・削除で後続イベントが `applied: false` になり得るが、通知は編集対象
    イベント分のみで、後続打席が打順表から無言で消える（lib/app-state/reducer.ts:117-138）。
    - 「この修正で後続 N 件が無効になります」の事前プレビュー（旧 PRD の再計算プレビュー構想）
    - 無効化されたイベントの常設バッジ/一覧表示（`AppGame.violations` は UI 参照 0 件のまま）
      データの信頼性に直結するため、実質 P1 相当の優先度。
11. **打者の進塁先を開放**
    打者の行き先が結果種別で固定（単打なら 1 塁のみ。runner-advance-sheet.tsx:189-216）。
    「エラーで打者二塁」「単打＋悪送球で二塁」が入力不可能で、代替入力（ツーベース扱い）で
    記録が歪む。
12. **併殺打・犠飛の表記を守る**
    併殺は内部で `otherOut` に潰され、打順表表示が「アウト」になる（event-factory.ts、
    notation.ts）。「遊併」等の専用表記、可能なら中継順（6-4-3）の保持。
    犠飛は方向を選べず「中犠飛」と書けない。
13. **細部の表現力**
    振り逃げ時の打者二塁以遠、本塁/三塁封殺の野選、二塁走者のタッチアップ三進の既定化。

## 5. P4: 一覧性・その他機能

14. **打順表の現在イニングへの自動スクロール**
    スコアボードには自動追従（scoreboard.tsx:25-31）があるのに打順表にはない。
    375px 幅で見えるのは 4〜5 イニングのため、6 回以降は気付けない。
15. **1 画面性の改善**
    667px 端末ではスコアボード＋状況カードで可視領域の約 6 割を占有し、打順表がほぼ見えない。
    スコアボードのコンパクトモード（現在イニング±1 と合計のみ、タップで展開）を検討。
16. **救援投手の成績**
    投手交代イベントは記録できるが、集計は先発のみで交代後は打ち切り（lib/domain/pitching.ts）。
    交代を跨いだ投手別集計へ。
17. **試合履歴への導線**
    履歴はセットアップ画面からのみ到達可能。結果画面ヘッダーにも導線を追加。
18. **打席途中の中断メモ**
    ボールカウント非記録の軽量さは強みとして維持しつつ、中断（雨・時間）時の軽いメモ手段を検討。

## 6. 品質・技術面

- **UI 層の自動テストがほぼゼロ**（feedback-dialog.test.ts のみ）。振り逃げ・打点保持・違反通知は
  いずれも「ドメインと UI の結線」に依存しており、ドメインテストでは回帰を検知できない。
  Testing Library で「結果選択→シート→確定→打順表反映」の主要フロー 3〜4 本を先に整備する。
- **型の二重管理**: UI 層はレガシー `lib/types.ts` の `AtBatResult` を使い続け、event-factory で
  常時変換している。ドメイン型（lib/domain/types.ts）への統一で変換層のバグ余地を除去。
- **未使用資産の一掃**: components/ui/ 配下の未使用 shadcn 約 40 ファイルと未使用依存
  （recharts, react-hook-form, zod, date-fns, embla-carousel, vaul, cmdk, input-otp,
  react-day-picker, next-themes 等）。バンドルサイズと監査ノイズの削減。
  `END_GAME` アクション（dispatch 箇所 0 件、テスト専用）も削除対象。
- **movements の暗黙契約の明示**: 配列順が「アウト成立順」を意味し 3 アウト目の得点判定が
  依存している（replay.ts:617-625）。最低限コメント化、できれば明示フィールド化。
- **実機確認の未実施**: P1/P2 はタップ感覚の問題のため、着手前にスマホで 1 試合通しで記録し、
  本書の優先度を体感と突き合わせることを強く推奨。

## 7. 推奨着手順

費用対効果が最大の 3 点から着手する。

1. 進塁シートのスキップ拡大 + 既定進塁の文脈対応（P1-1, P1-2）
2. 編集の連鎖無効化の可視化（P3-10）
3. 入力 UI の状況ミニヘッダ（P2-5）

以降は P2 の残り → P3 → P4 → 品質面の順。UI 層のフローテスト（6 章）は
P1 実装と並行して先に整備しておくと以降の改修が安全になる。

## 付録 C: 既定進塁（rules.ts）の提案品質と修正発生頻度

構造的な弱点: `getDefaultMovements(result, runners, batterId, currentOuts)` は
detail / battedBall（打球方向・内野/外野）を一切見ていない。

| ケース | 既定の挙動 | 実戦での修正頻度 |
|---|---|---|
| 単打・走者二塁 | second→third | **高**（外野単打では生還が普通） |
| 単打・走者一塁 | first→second | 低（適切） |
| 二塁打・走者一塁 | first→third | 中（生還ケースで修正） |
| ゴロ/フライアウト | 打者アウトのみ・走者据え置き | **非常に高**（封殺・進塁打・ゴロゴーが全て手作業） |
| 犠飛 | 三塁走者のみ生還 | 中（二塁走者のタッチアップ三進が既定にない） |
| 野選 | 一塁走者 force out + 打者一塁 | 中（本塁/三塁封殺の野選が表現できない） |
| 四球・死球 | 押し出しのみ・満塁時 RBI 付き | 低（適切） |
| エラー | 単打と同進塁・三塁走者 RBI=false | 中〜高（付録 D の入力不能問題あり） |
| 振り逃げ | 一塁空き=出塁 / 2アウト=フォース / 他=アウト | 中（ルール上正しいが期待と食い違いやすい） |
| 内野安打 | 通常単打と同一扱い | 高（三塁走者が自動生還してしまう） |

## 付録 D: 現状の UI では入力が不可能なケース

`getDestinationOptions`（runner-advance-sheet.tsx:189-216）が打者の行き先を結果種別で
固定しているため、以下は正しく記録できない（代替入力で記録が歪む）。

- エラーで打者が二塁まで進んだ（→ ツーベース扱いにするしかない）
- 単打＋送球エラーで打者二塁
- 野選で打者が二塁まで進む
- 振り逃げで打者が二塁以遠へ（1塁/アウトのみ。runner-advance-sheet.tsx:189-197）
- 走者を「アウト」に変更しても封殺/タッチの区別（outType）が付かない
- 併殺の中継順（6-4-3 等）の保持 — detail は守備位置 1 つのみ
- 犠飛の打球方向（「中犠飛」と書けない）

## 付録 E: レイアウト実測値（モバイル 375×667px 想定）

- スコアボード: 3 行 × 36px ≒ 110px
- 状況カード: ヘッダ行 48px + 本体 150px ≒ 200px
- sticky ヘッダ 52px + 下部固定バー領域 92px
- → 可視領域約 520px のうち約 310px をスコアボード + 状況カードが占有し、
  打順カードは 1〜2 行しか見えない（自分の打順・過去打席の確認に縦スクロール必須）
- 打順表: sticky 列 112px + イニング列 56px → 同時に見えるのは 4〜5 イニング。
  スコアボードにある現在イニング自動スクロール（scoreboard.tsx:25-31）が打順表にはない
- 進塁トグル: 5 択横並びで 1 個 ≒ 62〜68 × 40px（44px 基準未満、「ホーム」「アウト」が隣接）
- 満塁時の進塁シート: 走者 4 行 + プレビューで内容高 ≒ 670px > 88dvh ≒ 587px となり、
  確定ボタンがスクロール圏外に落ちる

## 付録 F: 補足の小粒な観察

- NEXT 打者番号の分母が `players.length` 固定（game-situation.tsx:94）で、交代により
  `activeLineup` と人数がずれた場合に番号がずれる懸念（通常は同数のため顕在化しにくい）
- トーストが top-center（app/layout.tsx:48）に出るため、下部で操作する親指の視線から遠い
- 打点指定の UI が不統一: 打席シートは走者ごとのチェックボックス、走塁シートは
  「打点として記録」+ 打者 Select（暴投生還時に手数が増える）
- 2 チームの打順はタブ切替（1800px 未満）で、守備側の投手確認に 1 タップ必要
- 走塁ボタンは走者不在時 disabled で妥当だが、打者走者が絡む振り逃げ・打撃妨害は
  打席フロー側にしかなく初見で探しにくい
- 3 アウト目の特定が movements の配列順依存（replay.ts:617-625）である契約が未明示
- `hooks/` と旧 `tasks/todo.md` の参照先（docs/plan.md、削除済み）が残骸として残存
